# Desktop integration

fff can be the machine's file manager, not only a launcher from the shell:
directories opened by other programs (`xdg-open`, a launcher, a browser's
"Show in folder") open in fff, and Firefox and other applications that use the
desktop portal pick files with it. `fff --setup` installs each part:

```sh
fff --setup desktop        # open directories in fff
fff --setup file-chooser   # pick files with fff in Firefox and other apps
```

Both run fff in a new terminal window using `[open] fff_terminal` from the
configuration (`st -c fff-picker -e` by default; see
[openers](CONFIGURATION.md#openers)), which a window manager can
[float](#floating-windows). Set it before running setup, and run setup again
after changing it or after moving the fff binary: the files it writes name
both.

## Floating windows

fff started from another program is a short-lived picker, best shown as a
floating window over the current layout rather than a new tile. The default
`fff_terminal`, `st -c fff-picker -e`, gives every such window the X11 class
`fff-picker`. fff does not float the window itself: that is up to your window
manager, which needs a rule for that class. In i3 (`~/.config/i3/config`),
for example:

```
for_window [class="fff-picker"] floating enable, resize set 1500 1000, move position center
```

With another window manager, write the equivalent rule in its own
configuration (sway: `for_window [app_id="fff-picker"] floating enable`;
dwm: a `rules[]` entry with class `fff-picker` and `isfloating` set), or pick
another class in `fff_terminal` and match that. Other terminals set the class
differently: `alacritty --class fff-picker -e`, `kitty --class fff-picker`,
`xterm -class fff-picker -e`, and on Wayland `foot --app-id fff-picker`. Use
the same class for your own launchers, e.g. `st -c fff-picker -e
findnotes-fff`, and they float alike.

Setup reports every file it writes or leaves unchanged on stderr. Files fff
generated (they say `Generated by fff --setup`) are replaced when run again;
any other file at the same path is never overwritten, and setup stops and asks
you to move it aside. Existing configuration files are edited one key at a
time, keeping everything else.

## Opening directories

`fff --setup desktop`:

1. Writes `$XDG_DATA_HOME/applications/fff.desktop` (`~/.local/share/...` by
   default), an application for `inode/directory` whose command is
   `FFF_TERMINAL fff --browse %f`, with the terminal's own output discarded
(st, for one, logs every escape sequence it does not support, and that log
would otherwise land in the shell that ran `xdg-open`).
2. Refreshes the desktop database with `update-desktop-database` when it is
   installed.
3. Makes it the default for directories with
   `xdg-mime default fff.desktop inode/directory`, naming the previous default
   and how to restore it. Without `xdg-mime`, it prints that command instead.

`--browse` starts fff at the path it is given rather than pinning it as a
search root; given a file, fff starts in its folder with the file highlighted.
Started from a menu without a path, fff browses as usual and resumes where the
last session ended.

The entry runs the terminal itself instead of setting `Terminal=true`: with
`Terminal=true` each launcher chooses the terminal from its own list (GIO, used
by Firefox and GTK applications, does not know st) without the window class,
so the window would neither float nor be the same from program to program.

Check it with:

```sh
xdg-mime query default inode/directory   # fff.desktop
xdg-open ~/Downloads                      # fff in a floating terminal
```

Leaving fff closes the window. The chosen directory has no shell to change
into, so the default mode simply ends; files open with their
[openers](OPERATIONS.md#opening-files) as usual.

Firefox's "Show in folder" asks a file manager over D-Bus
(`org.freedesktop.FileManager1`) and, when none answers, opens the containing
directory, which then opens in fff. The downloaded file is not highlighted in
that case, since only the directory is passed.

## Picking files in Firefox

Applications that use the xdg-desktop-portal FileChooser ask the portal for a
file dialog; [xdg-desktop-portal-termfilechooser](https://github.com/hunkyburrito/xdg-desktop-portal-termfilechooser)
answers by running a wrapper script that opens a terminal file manager. Install
it first (on Arch, the AUR package
`xdg-desktop-portal-termfilechooser-hunkyburrito-git`), then:

```sh
fff --setup file-chooser
systemctl --user restart xdg-desktop-portal
```

and in Firefox, open `about:config` and set
`widget.use-xdg-desktop-portal.file-picker` to `1`, then restart Firefox: it
reads the setting only when it starts. File dialogs then open fff.

If they still do not, check the portal on its own; this opens fff as Firefox
would:

```sh
gdbus call --session --dest org.freedesktop.portal.Desktop \
  --object-path /org/freedesktop/portal/desktop \
  --method org.freedesktop.portal.FileChooser.OpenFile "" "Test" "{}"
```

No fff window means the portal is the problem (`journalctl --user -u
xdg-desktop-portal` says which implementation it chose for the FileChooser);
a window means Firefox is not using the portal.

Setup changes three files under `$XDG_CONFIG_HOME` (`~/.config`):

| File | Change |
| --- | --- |
| `xdg-desktop-portal-termfilechooser/fff-wrapper.sh` | The wrapper script, written whole. |
| `xdg-desktop-portal-termfilechooser/config` | `cmd` names the wrapper, `create_help_file=0`, and `default_dir=$HOME` when unset. |
| `xdg-desktop-portal/portals.conf` | `org.freedesktop.impl.portal.FileChooser=termfilechooser` under `[preferred]`. |

When a desktop-specific file exists, it is edited instead, as each portal
reads that one first: `xdg-desktop-portal-termfilechooser/$XDG_CURRENT_DESKTOP`
and `xdg-desktop-portal/DESKTOP-portals.conf` (the desktop name lowercased).
Setup warns when it cannot find the portal's `termfilechooser.portal` file.
Replacing a previous `cmd` switches the dialogs from that wrapper to fff; set
it back to undo.

### Using the dialog

Each dialog runs `fff explorer`, a mode made for answering file dialogs. It
starts beside the file or in the folder the application suggests (`$HOME` when
it suggests none), and the empty query line says how to choose. Enter on a
folder enters it and Enter on a file chooses it, in Normal and Insert mode
alike; `q` and Ctrl+c cancel.

| Dialog | How to choose | Received |
| --- | --- | --- |
| Open a file (attach, upload) | Enter on a file | That file. |
| Open several files | Tab to mark, then Enter on a file or Ctrl+w | The marks and the file. |
| Choose a folder | Navigate into it and press `!`, or mark folders and Ctrl+w | Folders only. |
| Save (a download, a PDF from the viewer) | Navigate to the folder and press `!` | The suggested name in that folder. |

Saving needs no typing: `!` saves under the name the application suggests in
the folder you are browsing. When a file of that name exists, the new one is
numbered instead (`paper (1).pdf`); to replace a file, press Enter on it.
To use another name, rename the file afterwards (`r` in fff).

`fff explorer` works on its own too, printing the chosen paths one per line:

```sh
fff explorer ~/Downloads                 # choose one file
fff explorer --multiple --directory      # choose folders
fff explorer --save ~/Downloads/a.pdf    # where to save a.pdf
```

### The wrapper

The generated script records the fff binary and the terminal. `TERMCMD`, the
variable termfilechooser's own wrappers use, overrides the terminal for one
run or for good, e.g. from the portal configuration (keep a window class there
for the window to float):

```ini
[filechooser]
cmd=/home/you/.config/xdg-desktop-portal-termfilechooser/fff-wrapper.sh
env=TERMCMD=foot --app-id fff-picker
```

The terminal's own output is discarded unless the portal's log level is
debug. The terminal must stay open until fff exits (most do; a terminal that hands
the command to an existing server and returns at once cancels every dialog).
The script needs bash. With the portal's log level at debug
(`--loglevel=DEBUG`), it traces its commands in the
portal's log.
